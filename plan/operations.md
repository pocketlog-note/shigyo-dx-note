# 士業DXノート 週1回の運用手順

関連: [[CLAUDE]] / [[topics]] / [[log]]

定期タスク `shigyo-dx-note-weekly` は、このファイルの手順で動く。毎週木曜11時ごろに実行される（Claude アプリが起動しているとき。閉じていれば次に起動したとき）。1回の実行で公開する新しい記事は1本まで。

## 0. 前提
- 作業場所: `C:\Users\Administrator\Projects\play\shigyo-dx-note`。コマンドは `python -X utf8` で実行する。
- `CLAUDE.md`、このファイル、`plan/topics.md`、`plan/log.md` の最後の数件を読む。
- `git pull` して最新にする。`git status` で前回の作業の残りがないかを見る。

## 1. 公開済み記事の見直し（先にやる）
- `plan/topics.md` の「見直しが必要な記事」を見る。締切や日付が過ぎた記事があれば、公式の最新情報を確かめて記事を直す（例: 補助金の次の締切）。
- 直したら本文の最後の `:::method` に「YYYY年M月D日に追記：何を直したか」を書く。数字を直すときは出典も新しくする。
- 見直しは新しい記事の本数に数えない。

## 2. ネタを決める
- `plan/topics.md` の「候補」の上から選ぶ。尽きていたら、次の公式サイトの新着から、小さな士業事務所のIT・AIに関わる話題を探して候補に足す。
  - 中小企業庁・中小企業基盤整備機構（補助金）、デジタル化・AI導入補助金の事務局サイト（https://it-shien.smrj.go.jp/ ）
  - 個人情報保護委員会（https://www.ppc.go.jp/ ）
  - IPA（https://www.ipa.go.jp/ ）、デジタル庁、総務省、経済産業省
  - 国税庁（e-Tax、電子帳簿保存法）、厚生労働省・e-Gov（電子申請）
  - 日本税理士会連合会・全国社会保険労務士会連合会・日本行政書士会連合会の公開ページ
- 同じテーマの記事がすでにあれば、重ならない切り口にする。

## 3. 調べる
- 事実は公式の発表・資料（上のサイト、e-Gov法令検索）で確かめたものだけを使う。民間のまとめ記事・ブログは、公式資料を探す手がかりにだけ使い、記事の裏付けには使わない。
- PDF は保存して Python（`fitz`）で文字を取り出して読む。e-Gov の条文は built-in browser で `https://laws.e-gov.go.jp/api/2/` を使うと読める（ページ本体は JavaScript で描画されるため）。
- 確かめられなかったことは、記事に「確認できなかった」と書く。推測で埋めない。
- 会員専用の資料は、公開ページで分かること（題名・日付・概要）以外は書かない。

## 4. 書く
- `content/YYYY-MM-DD-<英小文字のslug>.md` を作る。書き方は `build.py` の冒頭と、既存の記事（`content/2026-11-24-*.md`）を手本にする。
- **本文は3,000〜8,000字**。字数を出すために同じことを繰り返したり、推測を足したりしない。公式資料の中身（条件、手順、日付、表）を増やして字数を満たす。
- 構成: リード（ファクトだけ）→ 見出しごとの本文（ファクトと表）→ `:::facts`（4〜5個、各行に出典リンク）→ `:::opinion 見出し`（ペン子の見解）→ `:::todo`（明日からできること1つ）→ `:::method`（読んだページと確認した日付）。
- ペン子の見解: です・ます調。ブロガーらしい語り口（「正直、」「〜なんですよね」「個人的には」）を使ってよい。ファクト欄にない数字は書かない。個別の法的判断や特定の製品のおすすめはしない。
- アイキャッチ: `big`（大きな数字や短い語）、`lines`（2行まで・1行16字程度まで）、`bubble`（2行まで・1行9字程度まで）、`label`（例: 締切が近い制度、公的機関の資料）。

## 5. 推敲と点検（毎回必須）
1. yomiyasu スキルで推敲する（種類は article）。推敲前の本文を `_text/<slug>-src.md` に置き、`yomiyasu_check.py run --source _text/<slug>-src.md --final content/<ファイル> --doc-type article --stance=説明 --fact-gaps`（資料があれば `--material`）と `verify` を実行する。
2. `python -X utf8 check.py` がエラー0件であること（本文3,000字未満、【要確認】残り、出典のないファクトはエラーになる）。
3. `python -X utf8 build.py` が通ること。
4. 数字・日付・条文番号を出典と1つずつ照らし合わせて読み直す。

## 6. 公開
- 手順5がすべて通ったら、`draft` を付けずに公開する（ユーザーの指示 2026-11-25「週1本で定期化」）。通らないときは `draft: true` を付けて残し、理由を記録と報告に書く。
- `git config --local user.email` が `359506683+pocketlog-note@users.noreply.github.com` であることを確かめてから、`git add -A` → `git commit`（「何を・なぜ」を1行）→ `git push`。
- 数分おいて、https://pocketlog-note.github.io/shigyo-dx-note/ で新しい記事が表示されることを built-in browser で確かめる。

## 7. 記録
- `plan/topics.md` から使ったネタを消し、締切や日付のある記事は「見直しが必要な記事」に追加する。
- `plan/log.md` に、日付・記事（URL）・公開か下書きか・見直した記事・次回への申し送りを1〜3行で追記して、コミット・push する。
- 完了報告は「何をしたか／確認できたこと／未確認のこと」に分ける。公開した記事があれば URL を最初に書く。

## やってはいけないこと
- 出典のない数字・制度・日付を書くこと。民間サイトだけを根拠にすること。
- 1回の実行で新しい記事を2本以上公開すること。
- 個人のメールアドレス・本名を出すこと。アカウント作成、X など外部への投稿（X は `x-drafts/` の下書きまで）。
- `git push --force`、履歴の書き換え、ファイルの削除。
